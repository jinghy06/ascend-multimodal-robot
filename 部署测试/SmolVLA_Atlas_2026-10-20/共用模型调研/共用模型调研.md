# 动作与问答共用模型：公开案例调研

检索日期：2026-10-20。只把作者论文、项目主页、官方代码与权重页作为结论依据；本轮未在 Atlas 安装这些项目或替换现有模型。

**结论：有公开案例，最直接的是 ChatVLA 和 DiffusionVLA。已有证据支持“同一模型做视觉问答和机器人动作”，但本次未找到可直接复现的“当前 SmolVLA 450M + 中文自由对话 + Atlas 310B / 3.5GB 内存”完整方案。**

## 1. ChatVLA：最值得借鉴的共享设计

作者将问答和控制放入同一个网络：共享注意力层，分别使用任务专属 MLP 专家，并通过阶段训练与视觉语言数据维持理解能力。这是部分参数共享，不是全部参数完全共用，也不是另挂一套独立聊天模型。[论文正文](https://aclanthology.org/2025.emnlp-main.273.pdf)

代码 `StaticMoE.forward(..., eval_in_vqa=False)` 在推理时选择问答专家或控制专家；源码可以直接检查这个分支。[专家选择代码](https://raw.githubusercontent.com/tutujingyugang1/ChatVLA_public/main/qwen2_vla/utils/expert_modules.py)

[作者仓库](https://github.com/tutujingyugang1/ChatVLA_public)提供训练、机器人评估、VQA 评估与权重入口，使用 Qwen2-VL-2B 作为基础骨干。不要把“2B 骨干”误认成整个模型仅 2B：[作者链接的权重页](https://huggingface.co/zzymeow/ChatVLA)标注整体约 3B 参数、BF16。

对于当前板子的判断：3B 个参数按每个 2 字节，仅参数约 6GB（十进制），尚不含缓存和运行时，超过板上 3513 MiB 可见内存。这是参数规模估算，不是本板部署测量。该项目适合借鉴架构，不能作为当前板即装即用的方案；量化和 NPU 适配也尚未验证。

## 2. DiffusionVLA / DiVLA：明确展示保留问答的动作模型

同一 VLM 提供文本生成/推理与动作条件，另接扩散动作分支。论文第 8.6 节、表 11 给出识物、颜色和场景描述的 VQA 示例，也报告错误案例，属于可核查的问答证据。[论文及 VQA 例子](https://arxiv.org/html/2412.03293v3#S8.SS6)

作者最小型号为 2B，展示的速度基于 NVIDIA A6000，不能移用到 Atlas。[作者项目主页](https://diffusion-vla.github.io/)

代码由 [DexVLA 仓库](https://github.com/juruobenruo/DexVLA)提供 DiVLA 训练脚本。需要区分：可以训练 DiVLA 不等于仓库中每个 DexVLA 权重都已验证同样的对话能力。这里的公开演示主要是视觉问答，不能直接推定中文长对话效果。

## 3. ChatVLA-2：问答结果直接用于选择动作

作者展示“读白板上的数学题并拿取正确答案卡片”、未见物体的空间摆放等任务，说明理解/推理能力能够与动作执行结合。[作者项目主页](https://chatvla-2.github.io/)

这是共享理解与控制的进一步例子，不是已经适配本板的轻量语音助手，也不是完整中文自由聊天评测。

## 4. LLaVA-VLA-0.5B：小模型候选，证据尚不足以当聊天方案

作者开放了基于 LLaVA-OneVision-Qwen2-0.5B 的动作模型、权重与训练入口；仓库还有动作专家版本。[作者仓库](https://github.com/OpenHelix-Team/LLaVA-VLA)

但公开 README 的主要结果是动作控制，未见与 ChatVLA 相同层次的聊天/VQA 保留证据。README 对小模型还提及 8GB GPU 环境，不能据名称“0.5B”就推定可在 3.5GB Atlas 上直接运行。[README 原文](https://raw.githubusercontent.com/OpenHelix-Team/LLaVA-VLA/main/README.md)

因此把它列为可继续研究的小模型候选，不列为已证实“中文聊天 + 抓取共用”的即用方案。

## 5. 常见假阳性：两套模型协作不等于权重共享

有些语音机器人方案使用高层 LLM 规划、低层 SmolVLA 执行。这能完成自然交互，但两套模型各自有权重，不能据此证明节省了对话模型的常驻内存。检索时也不把“理解语言指令”“输出动作前的推理语句”直接等同于自由问答。

## 对当前项目的选择

| 路线 | 与需求的关系 | 当前状态 |
|---|---|---|
| 直接照搬 ChatVLA / DiVLA | 已有问答与动作共用证据 | 规模偏大，未适配 Atlas，不建议直接替换主线 |
| 补齐完整 SmolVLM，抓取用前 16 层、文本用完整骨干 | 最接近现有权重的共享改造思路 | 工程推断，未找到相同板上的现成完整案例；需核对参数一致性、补权重、测中文与内存 |
| 基于小型中文 VLM，借鉴 ChatVLA 的共享/专家隔离训练 | 更贴近中文自由问答与小内存目标 | 需要训练与适配动作分支；不能把现有 SmolVLA 专家直接无验证地换接到 Qwen |
| Qwen 与 SmolVLA 分阶段运行 | 工程上可先独立推进 | 两套权重，不属于本次所说的共享；并发内存和完整语音链路仍未验证 |

研究建议：学习 ChatVLA 如何保留语言能力，将“恢复完整 SmolVLM 并复用”的小实验作为最近的可行性验证。先证明简单中文问答正常、再确认抓取输出不被破坏，最后测整机内存；不要仅因为两个入口都能运行就认定方案完成。

当前板上已测事实仍是：SmolVLA 的文本生成入口能够跑通，但 16 层裁剪权重的三条中英文基本问题均为无意义输出，CPU/NPU token 一致。参见 [本机语言复用测试](../语言复用测试/语言复用说明.md)。这不否定共享架构本身，说明需要保留或训练可用的语言能力。
